AI WEBSITE 專題企畫書

一、專題構想

本專題開發 AI WEBSITE，一個涵蓋「AI 知識與相關議題」的搜尋引擎。搜尋範圍包含技術概念、地緣政治、哲學、經濟、就業、法律與治理等，不以 LLM、RAG 或 AI Agent 為限制。系統依使用者想理解背景、比較觀點或了解研究與應用的需求，協助找到可直接開啟的原始資料。

使用者輸入關鍵字並選擇搜尋目的後，系統預設查詢 Wikipedia 與 Crossref 公開索引，不需要 API 金鑰；也可選配 Brave 搜尋更廣的網路資料。系統依取得的標題、摘要與需求訊號重新排名，結果提供真實來源網址。課程要求的網頁全文計數與網址樹，則透過另行選用的受限網頁抓取功能展示。

我們將先完成課程要求的關鍵字計數、網站樹與排名功能，再加入 Jev 協助判斷內容是否切題。若時間允許，進一步加入 RAG，將搜尋到的資料整理成附有來源的簡短回答。

本專題的目標是讓前幾筆結果更符合使用者的查詢目的，或縮短找到適合資料的時間。任何 AI 相關概念與議題都能送出查詢，不必先加入固定主題清單；但來源涵蓋率、網路狀態及關鍵字用法會影響結果，不能保證每個問題都有相關資料。是否優於一般搜尋引擎，將以固定測試題的實際比較結果判斷。

二、開發動機與使用情境

了解 AI 時，同一個主題可能同時出現在入門教學、研究論文、政策文件與社會討論中。有人想理解技術，有人關注 AI 對工作或國際關係的影響，也有人想比較機器是否可能具有意識的不同觀點。只收錄少數技術教材，無法滿足這些需求。

例如，使用者搜尋：
「RSI 是什麼」、「AI 對就業的影響」或「人工智慧地緣政治」

在 AI 語境下，RSI 指 recursive self-improvement（遞迴自我改進），搜尋時需要補充語境，避免只找到金融技術指標。搜尋就業影響時，則應優先找到相關研究與論點；單純出現很多次「AI」的技術教材不一定符合需求。

因此，我們希望讓 AI WEBSITE 除了比對關鍵字，也能考慮「這個網頁是否符合使用者這次想學的內容」，減少逐頁開啟與篩選的時間。第一版提供三種搜尋目的：
- 概念與背景：優先尋找有定義、背景說明與例子的內容。
- 觀點與比較：優先尋找有不同主張、適用情境、利弊與限制的內容。
- 研究與應用：優先尋找程式範例、應用案例、政策建議或實證研究。

例如，同樣搜尋 AI 就業影響，選擇「概念與背景」時重視背景說明；選擇「研究與應用」時，則重視案例與實證資料。技術問題仍可搜尋程式碼與操作教學。這些是排名設計目標，並非已驗證的優勢。

搜尋主題不限於以下例子：
- 技術與研究：RSI、AGI、模型訓練、LLM、RAG、AI Agent。
- 地緣政治與治理：晶片出口管制、算力競爭、AI 監管。
- 哲學與倫理：機器意識、對齊、偏見與責任。
- 經濟與社會：生產力、就業、所得分配、教育與著作權。

預設資料來源是 Wikipedia 與 Crossref 公開索引，前者提供百科內容，後者提供學術文獻資訊；這兩者不等於全網搜尋，也不保證有最新新聞或每篇論文的全文。設定 Brave 金鑰後可選用較廣的網路搜尋，候選來源不限定特定教學網域。自編示範資料只在使用者主動切換示範模式時使用，不冒充即時搜尋結果。

結果保留來源名稱與原始網址，使用者可點標題或原文連結開啟網頁。來源可用不代表內容一定正確，仍需查核日期、版本、論據及是否切題。技術教材可參考 Hugging Face 與 PyTorch，這些網站只是來源例子，不是搜尋範圍限制。

參考網址：
- Wikipedia：https://www.wikipedia.org/
- Crossref 公開 API：https://www.crossref.org/documentation/retrieve-metadata/rest-api/
- Brave Search API：https://brave.com/search/api/
- Hugging Face LLM Course：https://huggingface.co/learn/llm-course/chapter1/1
- Hugging Face AI Agents Course：https://huggingface.co/learn/agents-course/unit0/introduction
- PyTorch Tutorials：https://docs.pytorch.org/tutorials/

三、主要功能與課程要求

Stage 0：關鍵字計數
輸入允許抓取的網址與關鍵字，讀取頁面文字後回傳出現次數；與搜尋結果摘要的計數分開說明。

Stage 1：網頁排名
輸入多個網址與關鍵字，顯示各網頁的排名、分數與關鍵字次數。

Stage 2：網站排名
分析主頁與子頁面，建立網址樹，顯示各節點計數與網站總分。

Stage 3：改善搜尋引擎排名
使用者只輸入關鍵字，由公開索引或搜尋服務取得真實候選網址，再套用評分。索引摘要重排與另行抓取完整網頁的網站評分，需分開展示資料範圍。

Stage 4：語意分析與關鍵字擴展
從搜尋到的內容找出相關詞，加入下一輪搜尋。

Stage 5：線上網站或 App
提供可操作的搜尋頁面、學習目的選項、結果列表及網址樹。

Stage 6：與 LLM 比較
將搜尋策略整理成提示詞，蒐集並比較 LLM 服務的回答。

開發順序以 Stage 0 至 3 為優先，再完成關鍵字擴展、線上介面及 LLM 比較。Jev 與 RAG 的加入，不能取代課程要求的計數、樹狀結構與排名功能。

四、系統運作方式

1. 取得候選網頁

使用者輸入主題與需求，例如「AI 就業影響 實證研究」，並選擇「研究與應用」。系統預設透過 Wikipedia 與 Crossref 取得候選網址，也可選用 Brave，並保留來源提供的順序，供後續比較。不同來源的順位不能當成 Google 原始排名。

第一版可接受中文問題與英文專有名詞，整理部分常見中英對照，例如「地緣政治」對應 geopolitics、RSI 對應 recursive self-improvement，減少用詞不同造成的漏搜。對照表只協助查詢，不是可搜尋主題白名單；不在表內的字詞與中文複合問題仍保留。未含 AI 語境的查詢會補上 AI 相關詞，但不宣稱可完美理解所有縮寫與跨語言問題。

2. 抓取內容並建立網址樹

一般搜尋先使用來源回傳的標題與摘要，不假裝已讀過完整網頁。只有另行啟用 HTML 抓取時，才取得頁面文字、移除程式腳本與重複導覽內容，再找出允許範圍內的子頁面。抓取白名單是此項功能的安全邊界，不限制一般搜尋可顯示或開啟哪些網站。

網址樹以候選網址作為根節點，子頁面作為下一層節點。每個節點記錄：
- 網頁標題與網址。
- 資料語言、擷取日期，以及可取得的更新日期與工具版本。
- 各關鍵字的出現次數。
- 網頁分數。
- 子頁面清單。
- 抓取是否成功。

真實網站可能互相連結，因此需要記錄已處理的網址，避免重複抓取與無限循環。

測試時先用小型網站驗證完整走訪。實際 HTML 抓取限制為同主機與起點目錄、深度最多兩層，每次搜尋總抓取嘗試最多 40 次；失敗也計入預算。這項限制須向助教確認是否符合 Stage 2 的要求。摘要模式不產生完整網站樹，未完整抓取時須清楚標示。

3. 計算網頁與網站分數

第一版使用容易解釋的關鍵字計分方式。每個命中的詞加入 1＋ln（出現次數），再按文字長度調整，減少堆疊關鍵字及長文章的優勢。

常見中英對照詞可以一併查找，各詞的出現次數分開呈現。同義詞可能命中重疊的文字，因此不能把欄位相加當成「不重複詞數」。公開索引與搜尋服務模式計算的是標題及來源摘要，不是整頁全文；只有真正抓取 HTML 後，才能說明頁面文字的計數。

網站分數則整合主頁與子頁面：
網站分數＝主頁分數＋0.5 × 第一層平均分數＋0.25 × 第二層平均分數

例如主頁為 8 分、第一層平均為 6 分、第二層平均為 4 分，網站總分就是：
8＋0.5 × 6＋0.25 × 4＝12 分

這些權重是初始設定，之後會利用開發用題目調整，並在正式測試前固定。

完成基本排名後，再依查詢目的加入內容符合度。例如選擇「研究與應用」時，檢查是否有實作、案例或政策建議的訊號；選擇「觀點與比較」時，檢查是否討論差異、取捨或爭議。這些條件先用規則判斷，再測試加入 Jev 是否改善結果。基本分數與加強後的分數分開保存，方便解釋排名原因。

4. 擴展相關關鍵字

系統從本輪實際取得的摘要或網頁文字找相關詞，依目前整理的 AI 技術與社會議題詞彙表挑選少量詞，加入下一輪搜尋。這個詞彙表只限制自動加詞的能力，不限制原始查詢範圍。

例如搜尋 RAG 後，可能從內容找到 embedding、retrieval、chunking 等候選詞。系統會依原始問題篩選，記錄這些詞來自哪些網頁，以及加入後是否改善結果。

第一版先限制最多新增三個詞、再搜尋一輪，避免查詢逐漸偏離原始需求。

5. 顯示搜尋結果

搜尋結果頁預計顯示：
- 可點擊的網頁標題、原始來源連結與相關內容片段。
- 摘要或 HTML 文字等資料範圍，避免把摘要次數當成全文次數。
- 原始排名與重新計算後的排名。
- 網站分數與各關鍵字次數。
- 與查詢目的相關的標示，例如概念說明、觀點比較、應用案例；由模型判斷的標示須註明，不能視為品質保證。
- 可展開的網址樹。
- 新增的相關關鍵字。
- 抓取失敗或資料不完整的提示。

五、Jev 與 RAG 的用途

Jev：協助判斷哪些內容更切題

Jev 可接收內容與明確問題，回傳選擇或評分。我們預計將它用於兩個部分：
1. 搜尋結果重排：讀取取得的內容片段，判斷是否解釋指定的 AI 概念、比較相關觀點，或提供所需的實作步驟、案例與實證資料。若有版本或日期條件，也需檢查是否有明確資訊可支持。
2. 相關詞篩選：從網頁擷取出的候選詞中，選出適合加入下一輪搜尋的詞。

Jev 的評分會與基本規則分數分開保留，以比較加入模型後是否確實改善結果。內容難度與相關性的判斷需人工抽查；高分不代表說法正確，也不能僅憑頁面有程式碼就宣稱範例可以執行。若服務無法連線，系統仍可使用原本的規則排名。

RAG：根據搜尋資料整理回答

RAG 的意思是「先找資料，再依據資料生成回答」。

例如使用者詢問「RAG 和微調有什麼差別」，系統先找到相關段落，再交由文字生成模型整理重點，並附上來源連結。

Jev 本身不負責撰寫這類自由文字回答，因此若加入 RAG，需要另外串接文字生成模型。資料不足時，系統應明確表示無法確認，不自行補出沒有來源的內容。

RAG 列為延伸功能，優先度低於課程要求的搜尋、排名及比較實驗。

本專題中的 RAG 同時是「可搜尋的 AI 知識主題」與「系統可選用的回答技術」。即使第一版尚未提供 RAG 回答，使用者仍可搜尋 RAG 相關教材。

六、資料結構與演算法的應用

- 字串比對：計算關鍵字出現次數，銜接 HW3 的 Boyer–Moore 練習。
- Tree：表示主頁與子頁面的關係，儲存各節點分數。
- Queue 與 BFS：逐層處理待抓取網址，控制走訪深度。
- HashSet：記錄已處理網址，避免重複與循環。
- HashMap：儲存關鍵字次數、權重及網址對應資料。
- Heap 或排序演算法：依分數產生排名，或挑出前幾筆結果。

搜尋核心預計使用 Java 開發；搜尋 AI 知識不影響實作語言的選擇。報告除了展示功能，也會說明資料如何儲存、網址如何走訪，以及計數與排序的時間、空間成本。哪些結構必須自行實作，依老師與助教規定辦理。

七、如何比較搜尋效果

1. 準備測試題

預計準備 50 題，其中 20 題用於開發與調整，另外 30 題保留作正式測試。

題目涵蓋 AI 技術、地緣政治、哲學、經濟與社會議題，並分成概念與背景、觀點與比較及研究與應用三種目的，另加入新詞、縮寫、指定版本及資料不足的情況。每題事先訂定相關性標準，避免看完結果後才修改評分方式。

測試題示例：
- 概念與背景：「RSI 是什麼？與一般模型改進有何不同？」
- 觀點與比較：「支持及反對 AI 可能具有意識的論點是什麼？」
- 研究與應用：「AI 對就業影響有哪些實證研究？」
- 地緣政治：「AI 晶片出口管制會影響哪些國家與產業？」
- 技術實作：「找一個有 Python 程式碼的 Agent 工具呼叫教學。」

如果題目要求實證研究，只介紹名詞的文章就不能算完整符合需求。技術說法需回查原始文件或論文；社會與哲學議題則需區分事實、推論及不同立場，不把某一觀點或模型評分當作唯一標準答案。

2. 比較不同版本

- Google 原始結果：作為一般搜尋的比較基準。
- 搜尋服務原始結果：確認取得的候選資料本身有何差異。
- 自訂規則排名：檢查關鍵字與網址樹評分是否改善排序。
- 規則排名加 Jev：檢查 Jev 是否帶來額外改善。
- 加入相關詞後的搜尋：檢查關鍵字擴展是否找到更好的資料。

Wikipedia、Crossref 與 Brave 的結果均不當成 Google 結果。評估時分別記錄來源，另外比較取得來源摘要與完整 HTML 的差異。

比較 Google 時也提供相同的學習目的，例如將「入門解釋」或「Python 實作範例」寫入查詢，不讓我們的系統獨占這些條件。另比較同一批候選網址的原始排序與重排結果，區分資料來源與排名方法的影響。記錄查詢文字、日期、語言與地區設定。

3. 評估指標

- 前五筆相關比例：例如五筆中有四筆符合需求，就是 80%；不足五筆時，空缺算未命中。
- 查詢目的符合情況：想看背景時是否找到清楚說明，想比較觀點時是否有相關論據，想看應用時是否有範例或實證。
- 第一筆正確結果的位置：觀察使用者要往下找多久。
- 完成任務時間：從送出查詢到找到正確資料所需的時間。
- 版本符合情況：有指定版本時，結果是否適用。
- 系統等待時間：記錄抓取、排名與模型呼叫造成的延遲。

相關性由兩位組員分別判讀，盡量隱藏結果所屬系統，意見不同時再討論。同一網址的多個片段只算一筆結果，資料不足題另記錄誤導情況。正式測試前固定設定，並保留全部結果與失敗案例；計時測試則交錯安排系統使用順序，降低重做同一題的熟悉效果。

4. 與 LLM 服務比較

依 Stage 6 要求，將我們的搜尋策略整理成提示詞，例如明確指定 AI 主題、學習目的、工具版本、所需範例及來源要求。

對相同題目比較一般提問與加入搜尋策略後的提問，記錄模型、日期、是否啟用網路搜尋及完整輸出，再檢查答案是否切題、正確，以及來源是否支持說法。

若完成 RAG 回答功能，另外檢查生成的內容是否忠於來源、引用是否正確，以及證據不足時是否停止猜測。答案品質與搜尋排名分開評估。

若只有部分題型優於 Google 或 LLM，報告就限定在該範圍說明，不推論所有搜尋都比較好。

八、分工與時程

每組依課程規定由三至五人組成，可按照以下工作項目分工：

- 網頁與網址樹：網頁抓取、文字清理、子頁走訪、去重與錯誤處理。
- 計數與排名：關鍵字比對、權重設定、網站計分與排序。
- 介面與整合：搜尋服務串接、學習目的選項、結果頁、樹狀畫面、Jev 與部署。
